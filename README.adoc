= Javadrift

Javadrift finds documentation that has drifted away from your Java or Kotlin API:
missing types and methods, outdated calls, broken repository links and more.
It reads Markdown and AsciiDoc, compares references with source declarations or
compiled JVM classes, and reports the document location to fix.

The CLI needs JDK 17 or newer. Building Javadrift from source also needs Maven 3.9+.
Analysis is offline and never executes project code or examples.

== How it works

. *Read your docs.* By default, Javadrift scans the root README.md/README.adoc and
  Markdown/AsciiDoc files under docs/. It extracts code references and local links;
  ordinary prose is skipped.
. *Index the API.* It reads Java/Kotlin declarations without requiring a build.
  Available compiled classes add generated APIs and override source declarations.
  Dependency classes can be supplied with --classpath.
. *Compare and report.* A reference to a missing member produces a finding with
  the document file, line, check ID and explanation. Add --since to compare APIs
  with a Git revision and detect references to removed symbols.
. *Review, then enforce.* Start with --warn-only, fix findings or review a baseline,
  then let the CLI or build integration fail CI on new errors.

Javadrift resolves recognizable API references conservatively; it cannot prove
every example or prose claim correct. Java snippet compilation is an optional
check that must be enabled explicitly. See <<_current_limits,current limits>>.

== Download the CLI preview

Download javadrift.jar and javadrift.jar.sha256 from
https://github.com/bohdaq/Javadrift/releases/tag/v0.4.0[the v0.4.0 release].
Verify the checksum with sha256sum -c javadrift.jar.sha256 (or shasum -a 256 -c
on macOS), then run java -jar javadrift.jar check --root /path/to/project.

To fetch the CLI directly in a bootstrap script, pin the release tag and download
both assets from the GitHub Release:

[source,shell]
----
JAVADRIFT_VERSION=v0.4.0
BASE_URL="https://github.com/bohdaq/Javadrift/releases/download/${JAVADRIFT_VERSION}"
curl --fail --location --output javadrift.jar "${BASE_URL}/javadrift.jar"
curl --fail --location --output javadrift.jar.sha256 "${BASE_URL}/javadrift.jar.sha256"
sha256sum --check javadrift.jar.sha256       # Linux
# shasum -a 256 --check javadrift.jar.sha256 # macOS
java -jar javadrift.jar check --root /path/to/project
----

Release assets are suitable for the standalone JVM CLI. They are not Maven or
Gradle repositories: build plugins still need Maven/Gradle publication, a custom
Maven-compatible registry, or the local `mvn install`/`includeBuild` setup below.
Start with --warn-only while reviewing findings for your project.

== Try a small example

After downloading javadrift.jar, run these commands in the same directory. They
create a small Java project whose docs name a method that does not exist:

[source,shell]
----
mkdir -p demo/src/main/java/com/acme
cat > demo/src/main/java/com/acme/Greeter.java <<'JAVA'
package com.acme;
public class Greeter {
  public String greet(String name) { return "Hello, " + name; }
}
JAVA
cat > demo/README.md <<'DOC'
Call `com.acme.Greeter#hello()` to greet someone.
DOC
java -jar javadrift.jar check --root demo --warn-only
----

The result points directly to the stale reference:

[source,text]
----
README.md:1:7  error  JD002  com.acme.Greeter has no member `hello`
Checked 1 documents, 1 types; 1 findings.
----

Correct the documentation to use the existing method and run a strict check:

[source,shell]
----
cat > demo/README.md <<'DOC'
Call `com.acme.Greeter#greet("Ada")` to greet someone.
DOC
java -jar javadrift.jar check --root demo
----

The result is zero findings. No build or configuration file is needed for this
example. --warn-only returns success for findings so you can review them first;
without it, this example's stale reference returns exit code 1.

For your own project, replace demo with its root directory. To export findings:

[source,shell]
----
java -jar javadrift.jar check --root /path/to/project --format json --output findings.json
java -jar javadrift.jar explain JD002
----

== Checks at a glance

[cols="1,3,1",options="header"]
|===
|ID |What it checks |Default
|JD001 |Qualified project type no longer exists |Error
|JD002 |Known project type has no documented member |Error
|JD003 |Documented arguments match no public overload |Warning
|JD004 |Removed API is still documented; requires --since |Error
|JD005 |Documented API is deprecated for removal |Warning
|JD006 |Documented project dependency version is outdated |Error
|JD007 |Repository path or relative document link is missing |Error
|JD008 |Java snippet fails to compile; requires compiler/classpath setup |Off
|JD009 |Documented configuration key has no known declaration |Off
|===

Checks use available project inputs; for example, version checks need project
coordinates and a release version, and dependency APIs need a supplied classpath.
See <<_advanced_checks,advanced checks>> for optional checks and
<<_check_documentation,configuration>> to change severity or scope.

== Diagnose setup

The 0.4.0 preview adds doctor. With the downloaded CLI, run:

[source,shell]
----
java -jar javadrift.jar doctor --root /path/to/project
java -jar javadrift.jar doctor --format json
----

It checks configuration, selected docs/sources, compiled outputs, dependency
inputs, the baseline and Java/compiler availability, with advice for each issue.
It does not analyze stale references or modify project files. Exit codes are 0
for ready setup, 1 for warnings and 2 for invalid inputs. See
link:docs/doctor.adoc[setup diagnostics] for scope, compiler probes and classpaths.

== Check documentation

[source,shell]
----
java -jar javadrift.jar check --root /path/to/project
java -jar javadrift.jar check --root /path/to/project --warn-only
java -jar javadrift.jar explain JD002
----

Full scans check qualified project types (JD001), unique type/member references
(JD002) and repository paths (JD007). Bare names and prose are skipped. Java
public/protected declarations, records, enums and project inheritance are indexed.
Unknown inherited APIs and source-only Lombok members are skipped conservatively.

Default inputs are the root README.md/README.adoc and Markdown/AsciiDoc files
under docs/. Build outputs are excluded; test sources contribute type-name hints only.
Java parser failures are reported as errors rather than silently dropping types.

[source,yaml]
----
# javadrift.yml
docs:
  include: ['README.md', 'README.adoc', 'docs/**/*.md', 'docs/**/*.adoc']
  exclude: ['docs/archive/**']
sources:
  basePackages: ['com.acme']
checks:
  unknown-member: error
failOn: error
ignore: ['LegacyClient#*']
----

Exit codes: 0 for success, 1 for findings at the failure threshold, 2 for
invalid input/configuration. --warn-only leaves input errors as exit 2.

== Git history and legacy adoption

[source,shell]
----
java -jar javadrift.jar check --since origin/main --format github
java -jar javadrift.jar check --format json --output findings.json
java -jar javadrift.jar baseline
----

Fetch the base ref before diff mode. Source symbols are compared at the supplied
ref and HEAD; the current working-tree docs are scanned. Bare removed class and
method names are checked only when no matching name survives. Existing overloads
are not reported as entirely removed members.

Place an HTML comment containing javadrift:ignore-next immediately above an
inline reference or opening Markdown fence. In AsciiDoc use a line comment
containing javadrift:ignore-next above the reference or opening delimiter.

The baseline file accepts findings by document path, check ID and reference,
so adding lines above a known finding does not invalidate it. Regenerating a
baseline replaces it with all current unsuppressed findings. Review and commit
the file; newly introduced references still fail.

Use baseline --check to audit unused entries without writing, and baseline --prune
to remove them without accepting new findings. These commands accept --class-dir
and --classpath, just like check. Keep the scan scope and Git reference consistent
with the baseline's original review. See link:docs/baselines.adoc[baseline maintenance]
for exit codes, classpath setup and CI usage. These options require 0.3.0 or newer.

== Compiled projects and Maven

Compiled classes under Maven target/classes and Gradle build/classes/java/main
or build/classes/kotlin/main override source declarations. This covers generated
APIs and compiled Kotlin without executing class initializers. For custom outputs
use repeatable --class-dir options. Supply dependencies with --classpath using
the platform path separator. JD006 reads Maven coordinates or the project section
of YAML; Gradle users can set project.groupId/artifactId/version in YAML.

Version checking uses a non-snapshot project version or the highest local numeric
Git tag for a snapshot (optional v prefix). It never looks up releases online.
Without a release tag, snapshot projects skip JD006. Maven property placeholders
are expanded only from that POM's properties; unresolved placeholders are skipped.

Version 0.4.0 is available from Maven Central. Use this block in the reactor
root POM; no custom repository or local installation is needed:

[source,xml]
----
<plugin>
  <groupId>io.github.bohdaq</groupId>
  <artifactId>javadrift-maven-plugin</artifactId>
  <version>0.4.0</version>
  <inherited>false</inherited>
  <executions><execution><goals><goal>check</goal></goals></execution></executions>
</plugin>
----

The aggregator checks root docs against all selected reactor modules. It forks
the compile phase to make reactor class outputs available before root verify.
The plugin supports javadrift.since, javadrift.warnOnly, javadrift.config,
javadrift.format, javadrift.output and javadrift.skip system properties.
For a development checkout, run mvn install before using its plugin version.

See link:examples/published-maven/README.adoc[the published Maven CI sample]
for a standalone POM, a copyable warn-only workflow and strict adoption. Its
automated walkthrough starts with an empty local Maven repository and uses only
published 0.4.0 artifacts, without installing this checkout.

=== Maven from a custom repository

If your organization hosts the Maven plugin in Nexus, Artifactory, GitHub
Packages or another Maven-compatible registry, add that registry to the
`pluginRepositories` section of the consuming POM (or to a Maven settings
profile):

[source,xml]
----
<pluginRepositories>
  <pluginRepository>
    <id>company-releases</id>
    <url>https://maven.example.com/repository/releases/</url>
  </pluginRepository>
</pluginRepositories>
----

Keep credentials in `~/.m2/settings.xml` or your CI secret store; do not commit
them to the POM. The repository must contain the published Javadrift plugin,
core and their POM metadata. A GitHub Release download URL is an asset store,
not a Maven repository, so it cannot be used directly in `pluginRepositories`.
For an unpublished build use `mvn install` and the local Maven repository as
described above.

=== Gradle from a custom plugin repository

For a Maven-compatible internal registry, add it to `pluginManagement` before
the plugin is resolved:

[source,kotlin]
----
pluginManagement {
    repositories {
        maven { url = uri("https://maven.example.com/repository/releases/") }
        gradlePluginPortal()
        mavenCentral()
    }
}
----

If the plugin is published through a repository that requires authentication,
configure credentials through Gradle properties or the CI environment, for
example `repoUser` and `repoPassword`; keep those values out of source control.
The custom repository must expose Gradle plugin marker metadata and the
`javadrift-core` Maven module. A GitHub Release asset cannot be used as a
Gradle plugin repository. For a checkout without a published plugin, retain
`includeBuild("/path/to/Javadrift")`.

The analysis engine uses the consumer's dependency repositories, separately from
plugin resolution. Add the same custom Maven repository to `repositories` in
build.gradle.kts, with `mavenCentral()` for third-party engine dependencies. With
a source checkout, the second includeBuild above substitutes local core instead.

The javadriftCheck task joins check and compiles Java source sets in the project
and its subprojects first. It writes a report under the build reports directory.
Use javadrift.since and javadrift.format extension properties for history and
output. Full scans can be up to date; diff mode always runs. Configuration,
baselines, Git refs and repository file changes are tracked as inputs.

== GitHub Actions and SARIF

The composite action lives in javadrift-action/. It requires a release tag with
the CLI jar and SHA-256 checksum. The release workflow produces those assets
when a version tag is pushed. Version v0.4.0 adds setup diagnostics to baseline
maintenance, isolated Gradle analysis and optional-check setup examples.
The runner needs JDK 17+; diff mode also needs a checkout with full history.

[source,yaml]
----
steps:
  - uses: actions/checkout@v4
    with:
      fetch-depth: 0
  - uses: actions/setup-java@v4
    with:
      distribution: temurin
      java-version: '17'
  - uses: bohdaq/Javadrift/javadrift-action@v0.4.0
    with:
      version: v0.4.0
      warn-only: 'true'
----

[source,shell]
----
java -jar javadrift.jar check --format sarif --output findings.sarif
----

SARIF 2.1.0 includes stable rule IDs, locations and baseline fingerprints. Use
GitHub's upload-sarif action with the generated report; grant security-events
write permission in that consuming workflow.

== Advanced checks

JD003 validates argument counts and clear literal types against overloads,
including varargs. It leaves unknown expression types alone. JD005 flags
references to types or members deprecated with forRemoval=true. Both default
to warnings; set failOn to warning to enforce them.

JD008 and JD009 remain off by default. Enable them explicitly:

[source,yaml]
----
checks:
  snippet-compile: warning
  unknown-property: warning
snippets:
  imports: ['com.acme.OrderService']
  release: '17'
----

JD008 compiles each Java fence as a complete unit, class members, then statements.
Supply compiled project classes and dependencies first. Annotation processing
is disabled and bytecode stays in memory. A line consisting of three dots, a
Java comment containing only three dots, or a javadrift:skip line comment skips
the whole block. Every block is isolated; variables do not carry between fences.
Complete units with package declarations must supply their own imports.
Compilation uses a JDK and the configured release (17 by default).

JD009 checks dotted inline keys and dotted assignments in code blocks against
production .properties/YAML resources, Spring configuration metadata in source
resources, literal System.getProperty calls and Spring Value annotations.
Third-party keys, dynamically declared keys and source-only ConfigurationProperties
beans without metadata need ignore patterns. It does not infer arbitrary Java
configuration APIs or every YAML example's intended schema.

Follow link:docs/optional-checks.adoc[optional checks setup and validation] for a
runnable Jackson-backed sample, complete dependency classpaths on Linux/macOS and
Windows, reviewed stale cases, and warning/strict behavior.

== Current limits

Java and Kotlin sources are indexed without building upstream projects. Kotlin
uses a syntax parser to index public/protected classes, interfaces, objects,
companions, properties, functions, aliases and project extension functions.
Private/internal declarations and test sources are excluded from the public API.
Their existing type names can resolve documentation references without exposing members. Default arguments
and trailing varargs contribute conservative signatures. Source properties and
default argument signatures remain available alongside compiled JVM methods.
Git diff mode compares both Java and Kotlin declarations.

This is declaration indexing, without Kotlin compiler type resolution. Imported
aliases, dependency extensions, Kotlin-specific compiler plugins and JVM name
mangling are not fully resolved. Non-final varargs are treated conservatively;
Kotlin deprecation levels are not modeled as Java forRemoval. JD008 compiles Java
snippets only. The embedded Kotlin parser adds roughly 60 MB to the CLI download.

AsciiDoc support covers backtick
code, source/listing blocks and link/xref targets; it does not expand include
macros, attributes or resolve anchors. Markdown anchors and external URLs are
not checked. Build class outputs before checking so they describe current sources.

The 0.4.0 preview implements all nine check IDs and build integrations.
The small corpus does not establish broad accuracy; adoption gates and the
Gradle Plugin Portal's first-publication approval remain pending. Maven Central
artifacts are published. See
link:docs/validation.adoc[validation evidence] and link:docs/roadmap.adoc[roadmap].

== Corpus-driven precision rules

An inline empty-parentheses reference such as JavaFile.writeTo() names a method;
its arity is checked in fenced examples, or when inline arguments are supplied.
Links escaping the checkout (including GitHub wiki and sibling repository links)
are outside the repository-path check.

Source indexing uses src trees and flat root Java files. Other Java templates
are skipped. Source variants with the same qualified name contribute their API
union, conservatively; compiled outputs replace that union with the selected API.
Use --class-dir for nonstandard build output layouts.

== Documentation path context

Inline paths can resolve from the document's module or documentation workspace as
well as the repository root. Outside root documents, bare build filenames and
inline directory mentions are treated conservatively as consumer-project conventions.
Explicit links and named source files still report missing targets. Home-directory
path fragments are not interpreted as repository paths.

For Maven site inputs, linked HTML can resolve to its Markdown/AsciiDoc input.
Generated Javadoc routes can resolve to an outer Java source file, package directory
or module POM. This checks source-backed paths without building a site; it does not
validate generated nested-class pages or anchors. Extensionless AsciiDoc xrefs are
same-document anchors. Symlinked documentation resolves links from its actual source
directory. GitHub contribution-template links can use the repository root context.

== Historical documentation and type ownership

Changelogs, CHANGES/HISTORY files and release-notes documents describe older APIs.
By default their API, version, property and snippet checks are skipped in both
full and diff scans; repository links and paths are still checked. Override
this scope with docs.historical (an empty list checks every included document):

[source,yaml]
----
docs:
  historical: []
----

Existing test, test-fixture and Maven site example declarations provide type-name
hints, without contributing public APIs or member checks. Malformed auxiliary
sources are ignored; malformed production sources remain input errors. JVM nested
names such as Outer$Inner resolve to source names, and Kotlin ::class is a class literal.

Without sources.basePackages, unknown-type checks use packages actually represented
in the public index and known outer types. Mixed library/example projects skip
conventional example, com.example and org.example namespaces. This avoids claiming
ownership of optional dependencies and consumer placeholders, but can miss a stale
type in a removed or mistyped subpackage. Configure sources.basePackages with your
project namespace roots to enforce checks across all their subpackages, including
example namespaces. Existing APIs and member references remain checked.

== Reference context

PlantUML, Mermaid, DOT and Graphviz blocks do not undergo Java API checks;
ordinary Java blocks still do. Javadoc links supply the owner of short member
labels, so a linked java.time.Clock method is not checked against a local Clock.
External API validity requires a configured classpath; external URLs are not fetched.

GitHub tree/HEAD and blob/HEAD links resolve against repository files, including
multiline Markdown links. Inline src/main, src/test and src/testFixtures directory
conventions can resolve to an existing module directory; explicit file links remain
relative to their document. No module source filename is inferred from another module.

An unknown qualified type can also be checked when its simple name matches a known
project or helper declaration sharing at least three namespace components. This
recovers mistyped packages while keeping unknown optional dependency namespaces
outside inferred ownership. Configure sources.basePackages for complete namespace
coverage; duplicate simple names and cross-project naming can still be ambiguous.

== Declared document exceptions

When a document deliberately mentions an old or third-party API, or links an
optional consumer file, declare the exception in docs.exemptions. Each entry
requires a file glob, check ID, reference glob and review reason. The optional
kind limits it to inline code (CODE), fenced/listing code (BLOCK), or links (LINK).
Other files, references and checks continue to report findings. These exceptions
apply to full scans and history findings and are opt-in; defaults are unchanged.

[source,yaml]
----
docs:
  exemptions:
    - file: '**/migration.adoc'
      check: JD001
      reference: 'old.api.*'
      kind: CODE
      reason: Inline names describe the old library API
    - file: '**/configuration.md'
      check: JD007
      reference: dictionary.txt
      kind: LINK
      reason: Optional consumer override file
----

Use exact file/reference patterns when possible. Exceptions express reviewed intent;
they do not prove that the referenced third-party API or optional file is valid.

== Continuous validation

The pinned validation workflow runs on pushes and pull requests using the current
source-built CLI. It checks both corpus scopes against active triage, fails when a
known error disappears or an unreviewed finding appears, and replays five reconstructed
and four naturally stale Java/Kotlin source-history cases. Reports are uploaded as the
pinned-validation-reports artifact, including after validation failures.
See link:docs/triage.adoc[reviewing findings and updating exceptions].

The performance workflow compares large Java and mixed Java/Kotlin scans against
the reference commit on the same runner. It records repeated scan times and peak
RSS, flags substantial regressions, and uploads the javadrift-performance artifact.
See link:docs/performance.adoc[benchmark commands, measurements and thresholds].
